By default, WebGPU rendering runs on the JavaScript thread alongside React. 
Using [React Native Worklets](https://github.com/margelo/react-native-worklets), you can run WebGPU rendering on the UI thread or on a dedicated worklet runtime.
There is even an experimental [Bundle Mode](https://docs.swmansion.com/react-native-worklets/docs/bundleMode/) that lets you run complex Three.js scenes on a dedicated thread.
You can see an example of Bundle Mode working with Three.js [here](https://github.com/software-mansion-labs/Bundle-Mode-showcase-app).

## Requirements

```npm
npm i react-native-worklets
```

Follow the Worklets installation guide for the babel plugin and native setup. WebGPU objects are automatically registered for Worklets serialization when the module loads - you can pass `GPUDevice` and `GPUCanvasContext` directly to worklets.

## installWebGPU

Worklet runtimes start without the WebGPU globals (`navigator.gpu`, the flag constants, the WebGPU classes). Call [`installWebGPU()`](/api/install-webgpu) once at the top of a worklet to install all of them for that runtime:

```tsx twoslash
import type { RNCanvasContext, CanvasRef } from "react-native-webgpu";
import type { RefObject } from "react";
declare const size: number;
declare const adapter: GPUAdapter;
declare const canvasRef: RefObject<CanvasRef>;
// ---cut---
import { Canvas, installWebGPU } from "react-native-webgpu";
import { scheduleOnUI } from "react-native-worklets";

const renderFrame = (device: GPUDevice, context: RNCanvasContext) => {
  "worklet";
  installWebGPU();

  const buffer = device.createBuffer({
    size,
    usage: GPUBufferUsage.COPY_DST | GPUBufferUsage.MAP_READ,
  });

  const commandEncoder = device.createCommandEncoder();
  // … encode passes …
  device.queue.submit([commandEncoder.finish()]);
  context.present();
};

// Create device on main thread, then run render on the UI thread:
const device = await adapter.requestDevice();
const context = canvasRef.current!.getContext("webgpu")!;
scheduleOnUI(renderFrame, device, context);
```

## Thread safety

The pattern above (create the device on the JS thread, render from a worklet runtime) is safe: a device and its resources (buffers, textures, pipelines, the queue) can be used from several threads. Prefer a clear ownership model all the same, setting resources up on one thread and rendering on another, and follow two rules:

- **Never share a command encoder across threads.** Create the `GPUCommandEncoder` (and its pass encoders) on the thread that uses it.
- **Don't drive the same canvas context from two threads.** Keep `configure()`, `getCurrentTexture()`, and `present()` for a given context on a single runtime.

Heavy simultaneous use of one device from many threads is not a supported use case: keep cross-thread traffic to handoffs.

A device that is only ever used from one thread can skip the synchronization with [`implicitDeviceSynchronization: false`](/api/gpu-device-extensions#implicitdevicesynchronization). Such a device must never be touched from a worklet runtime.
