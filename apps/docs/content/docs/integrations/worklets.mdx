By default, WebGPU rendering runs on the JS thread alongside React.
Using [React Native Worklets](https://github.com/margelo/react-native-worklets), you can run WebGPU rendering on the UI runtime or on a dedicated worklet runtime instead. Reanimated is not required, but if you already use Reanimated 4 you already have Worklets.
There is even an experimental [Bundle Mode](https://docs.swmansion.com/react-native-worklets/docs/bundleMode/) that lets you run complex Three.js scenes on a dedicated thread.
You can see an example of Bundle Mode working with Three.js [here](https://github.com/software-mansion-labs/Bundle-Mode-showcase-app).

This page covers the setup. [Threading](/docs/getting-started/threading) explains the model: the three runtimes and when to pick each, what has to stay on the JS thread, how objects cross, where promises settle, and a complete render loop that stops on unmount.

## Requirements

```npm
npm i react-native-worklets
```

Follow the Worklets installation guide for the babel plugin and native setup. WebGPU objects are automatically registered for Worklets serialization when the module loads: any WebGPU object (`GPUDevice`, `GPUCanvasContext`, pipelines, buffers, textures, ...) can be passed to a worklet as an argument or captured in its closure. They cross by reference, without a copy.

## installWebGPU

Worklet runtimes start without the WebGPU globals (`navigator.gpu`, `RNWebGPU`, `GPUBufferUsage`, `GPUTextureUsage`, etc.). Call [`installWebGPU()`](/api/install-webgpu) once at the top of a worklet to install all of them for that runtime:

```tsx twoslash
import type { RNCanvasContext, CanvasRef } from "react-native-webgpu";
import type { RefObject } from "react";
declare const size: number;
declare const adapter: GPUAdapter;
declare const canvasRef: RefObject<CanvasRef>;
// ---cut---
import { Canvas, installWebGPU } from "react-native-webgpu";
import { runOnUI } from "react-native-worklets";

const renderFrame = (device: GPUDevice, context: RNCanvasContext) => {
  "worklet";
  installWebGPU();

  const buffer = device.createBuffer({
    size,
    usage: GPUBufferUsage.COPY_DST | GPUBufferUsage.MAP_READ,
  });

  const commandEncoder = device.createCommandEncoder();
  // … encode passes …
  device.queue.submit([commandEncoder.finish()]);
  context.present();
};

// Create the device and get the context on the JS thread, then render on the UI runtime:
const device = await adapter.requestDevice();
const context = canvasRef.current!.getContext("webgpu")!;
runOnUI(renderFrame)(device, context);
```

This renders a single frame. For a continuous loop that stops on unmount, and for the dedicated-runtime variant, see [A render loop on a worklet](/docs/getting-started/threading#a-render-loop-on-a-worklet).

## Thread safety

The pattern above (create the device on the JS thread, render from a worklet runtime) is safe because `requestDevice()` enables Dawn's `implicit-device-synchronization` feature by default. It is coarse-grained locking, not a license for arbitrary concurrency: never share a command encoder across runtimes, and keep a given canvas context on one runtime. [Thread safety](/docs/getting-started/threading#thread-safety) has the details and the `implicitDeviceSynchronization` opt-out.
